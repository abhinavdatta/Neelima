### Shared contract and pipeline changes

- One correlation ID per send (`<task_id>.<8 hex>`), generated in Rust, echoed by the page on every `assistant_message`, `assistant_partial`, and `watch_state`. Rust rejects a push whose request ID is missing, mismatched, from a stale runtime, or with a non-increasing sequence, and emits `assistant-push-rejected` with a reason instead of silently dropping it.
- Lifecycle states surfaced as metadata-only `provider-request-state`: `submitted`, `submission_unconfirmed`, `completed`, `timed_out`, `cancelled`. `watch_state` reports `generation started`, `reply stable; confirming once more`, `waiting for a new assistant reply`, `completed`; it never carries page text.
- Reply baseline = assistant count + last assistant text captured immediately before the click, plus a page-side text snapshot; assistant count alone is not treated as novelty (reused containers).
- Completion rules: configured stop control is authoritative when present; otherwise two independent quiet windows with equal content are required. A quiet page with no new reply keeps waiting under the overall deadline instead of falsely completing.
- DOM-drift survival: detection falls back to the sibling following the last confirmed user turn, and the watch observes `document.body` rather than a conversation container that an SPA may replace.
- Backstop: read-only `capture_reply` polls after 5 s and delivers only a non-empty, new, stable candidate with no visible stop control; it never resends. Manual "Capture current reply" uses the same page method.
- Honest submission: a click alone is never success. Confirmation requires a matching new user turn (or composer-cleared plus stop control/new assistant turn). Unconfirmed sends are reported as `send_unconfirmed`, are never retried automatically, and get a bounded wait with an explicit unknown-outcome message.
- Provider chrome is stripped from pushed text before delivery; citation tokens are removed before copy-control lines so a `Copy 【cite】` line cannot leave a bare `Copy` in the reply.
- The page reports `visibilityState=visible` to its own logic so WebView2 throttling cannot freeze the completion watch while the pane is parked.

### Phase B — full response contract

- Lifecycle states now emitted end-to-end as metadata-only `provider-request-state`:
  `created` (request ID assigned) → `submitting` (immediately before the send RPC) → `submitted` or `submission_unconfirmed` → `streaming` (first partial preview only) → exactly one of `completed`, `failed`, `timed_out`, `cancelled`.
- `allow_request_state` (unit-tested) suppresses any transition after a request's terminal state, so racing error paths and late partials cannot double-finish a request. A different request ID starts a fresh lifecycle.
- Failures carry a coarse `error_category` (`login_required`, `page_unavailable`, `page_changed`, `timeout`, `send_failed`, `provider_error`) and never page text.
- The backstop capture path now closes the lifecycle with `completed` as well (before waking the agent), so the contract is identical whether the page watch or the Rust safety net delivers the reply.
- Every send resets `response_error`, `request_terminal` and `request_streaming`; a page reload (`on_page_ready`) does the same and drops the active request.

### Phase C/D — submission, cancellation, provider errors

- A page-side `SEND_IN_FLIGHT` guard refuses a second concurrent `send_message` with `error_type: "busy"` **without touching the page**, so an overlapping call can never type/click twice. Rust maps it to `send_failed`.
- A new `cancel_response` page method tears down the active completion watch (observer disconnected, timers cleared). Rust calls it on cancel, timeout, and before a superseding watch; a late reply from an abandoned round cannot push into the next request.
- Provider errors during generation are now detected without provider-specific error selectors: if the stop control was observed, has disappeared, and two quiet windows pass with no new assistant turn, the page posts `response_error` (code `provider_error`, bounded message), Rust emits `failed(provider_error)` and wakes the reply waiter immediately instead of waiting out the 7-minute deadline. Providers without a stop control (Gemini) keep the honest deadline.

# Step 2 — Reliable request tracking & lifecycle management (2026-10-22)

## Phase A — Audit of the existing request lifecycle

### How a request actually moves through the system today

1. **User action → request creation.** `ui_task_start` (ui.rs) creates the
   `task_id`; the frontend additionally mints `taskStartRequestId` and matches
   it against the `task-started` event before adopting the task (App.tsx). The
   app runs **one agent task at a time** (`ActiveAgent(Mutex<Option<Arc<AgentShared>>>)`
   in agent.rs) — this serialization is an intentional concurrency limit.
2. **Provider selection.** `build_provider` (ui.rs) resolves `web:<profile>` /
   `ollama` / `lmstudio` / `manual` into the `Provider` enum (providers.rs:
   `Web | Local | Manual`). The agent loop drives the same
   `send(task_id, conversation_id, text, first_of_task)` →
   `wait_reply(cancel)` interface for every variant.
3. **Submission.** Web: `WebProvider::send` (webprov.rs) mints
   `request_id = {task_id}.{uuid8}`, stores it as `active_request`, emits
   `created`, then drives `submitting → submitted` (or
   `submission_unconfirmed`) through the adapter runtime. Local: `send` merely
   queues the user message in `LocalProvider.messages`; the HTTP POST happens
   later inside `wait_reply`. Manual: `send` emits `relay-outbound` for the
   user to copy.
4. **Response capture.** Web: the page pushes `assistant_message` /
   `assistant_partial` keyed by echoed `request_id` + a per-request `seq`
   baseline; Rust rejects stale/foreign pushes. Local: NDJSON/SSE chunks are
   re-emitted as `assistant-stream` **with no request identity at all**.
5. **Backend delivery → frontend update.** Agent replies become transcript
   entries; live previews arrive as `assistant-stream` (local, append) or
   `assistant-partial` (web, replace). The frontend wait card is driven by
   `provider-request-state` events reduced in `ui/src/providerStatus.ts`.
6. **Completion.** `DONE:`/final reply ends the task (`finish`), errors go
   through `finish_error`; loading state is cleared via `agent-state` events.

### Existing request-identity machinery (browser only)

- `webprov.rs`: `REQUEST_*` state constants, `is_terminal_request_state`,
  `allow_request_state` (terminal guard: at most one terminal per request_id,
  a new request_id resets the marker), `emit_request_state` (metadata-only
  `provider-request-state` events), per-`WebviewState` `request_terminal`,
  `active_request`, response `seq` baseline, and a bounded `provider_events`
  trail in the UI.

### Defects recorded before changes (Step 2 scope)

- **D1 — Local/manual providers have NO request lifecycle.** No `request_id`,
  no `provider-request-state` events, no submitted-vs-completed distinction,
  no terminal reporting. The frontend wait card is literally gated to
  `providerSelected.startsWith("web:")`, so local models show only a generic
  spinner with no failure/timeout visibility beyond agent-loop errors.
- **D2 — `assistant-stream` chunks carry no correlation identity.** A late
  chunk from an aborted/previous local request, or after task switch, is
  appended to whatever `streamText` is currently shown (App.tsx gates only on
  `agentState === "waiting_for_ai"`). Web partials are protected in Rust by
  the seq/request-id gate; local chunks are not protected anywhere.
- **D3 — Submission acknowledgment is indistinguishable from completion for
  local providers.** The POST happens inside `wait_reply`, so "the runtime
  accepted the generation request" and "the reply finished" are the same
  event (or no event).
- **D4 — Cancellation has no `cancel_requested` state.** Stop jumps straight
  to `cancelled` (via `reply_wait_state("stopped")`), so "cancel requested"
  and "cancel completed" cannot be distinguished, and a reply that completes
  *despite* a cancel is indistinguishable from a normal completion.
- **D5 — No central request registry.** Browser request state lives inside
  `WebviewState`; there is no provider-independent record of requests, so
  diagnostics cannot answer "what happened to the last N requests across all
  providers".
- **D6 — Local timeout is hard-coded (600 s)**, not configurable like the web
  adapters' `response_timeout_ms`.
- **D7 — Late-event durability.** After a local timeout/cancel, chunks already
  in the mpsc channel can still be emitted once more before the abort lands;
  nothing re-checks request liveness at emit time.
- **D8 — `unknown` outcome state does not exist** in the model (reserved).

### Concurrency & correlation facts to preserve

- Exactly one agent task runs at a time (ActiveAgent); requests are per-round
  inside a task. This limit is intentional and stays.
- Web correlation: request_id echo + seq baseline + adapter-id scoping.
- Local conversation identity: the `LocalProvider.messages` vec lives for one
  agent task (recreated per task), so `task_id` is the strongest available
  conversation identity for local providers. Documented limitation: local
  runtimes expose no conversation id.
- Manual relay: task-scoped via `RelaySlot.live` task id.

Scope: one provider-independent request lifecycle for browser providers

### Phase B/C — canonical model and validated state machine (`src-tauri/src/request.rs`)

- `RequestRegistry` is the single, thread-safe, shared record of requests. One
  `RequestRecord` per request carries `request_id`, `provider_id`, `task_id`,
  `conversation_id`, `status`, `error_category`, `created_at_ms`,
  `updated_at_ms`. **No field can hold prompt or reply text** (test
  `snapshot_is_bounded_and_metadata_only` and `event_payload_is_metadata_only`
  assert the payload keys).
- Request IDs are minted per provider send (`{task_id}.{uuid8}`) and a repeated
  `begin` is refused, so an ID is never reused (`request_ids_are_unique_and_never_reused`).
  Provider, conversation, task and request identity stay separate fields.
- An explicit transition table (`transition_allowed`) is the only way a status
  changes; anything unlisted is rejected and nothing is emitted
  (`invalid_transitions_are_rejected_and_leave_state_unchanged`). Terminal
  states (`completed`, `failed`, `timed_out`, `cancelled`, `unknown`) accept no
  further transition, so a completed request cannot go active again and a
  duplicate terminal event is dropped while the first outcome is preserved
  (`duplicate_terminal_and_late_events_are_suppressed`).
- `cancel_requested` is distinct from `cancelled` and is NOT terminal; a reply
  that lands after a cancel is reported truthfully as `completed`
  (`cancel_requested_is_distinct_and_completion_despite_cancel_is_truthful`).
- `unknown` exists so an indeterminate outcome is representable instead of
  being forced into a wrong specific state; it is currently produced only by
  the browser-extension interrupted-request path (Rust-side it is reserved).
- Acknowledgment ≠ completion: `submitted` is recorded when the runtime/page
  accepts the generation request, `completed` only when a non-empty reply
  arrives.
- The registry is bounded (last 64 requests) so it can never grow without
  limit, and rejects transitions for unknown requests
  (`transitions_for_unknown_requests_are_rejected`).

### Phase D — provider integration

- `emit_request_state` (webprov) and `LocalProvider::emit_state` both route
  through the shared registry instead of per-provider terminal flags, so web,
  local and manual providers share one lifecycle and one event contract.
- Website-specific DOM behaviour stays in the adapter runtime/JSON adapters;
  local runtime HTTP behaviour stays in `providers.rs`. The registry contains
  no provider-specific selectors and no assumption that every provider streams.
- Capability honesty: web providers report `submission_unconfirmed` when the
  page cannot confirm the send; local runtimes confirm the POST; the manual
  relay reports `submitted` when the prompt is handed to the user. Cancellation
  is implemented for local (abort) and web (adapter stop control) and reported
  as `cancel_requested → cancelled`.
- Manual relay (`providers.rs`, `REQUEST_SUBMITTED/COMPLETED/FAILED/TIMED_OUT/
  CANCEL_REQUESTED/CANCELLED`) now reports the same states as the other kinds.

### Phase E/F — correlation and isolation

- Every response update is gated by `request_id` plus provider identity; the
  page must echo the active request's ID and a strictly increasing `seq` from
  the current runtime (`assistant_push_must_match_the_active_request_id`,
  `assistant_sequence_accepts_only_current_runtime_and_strictly_new_sequences`).
- Local `assistant-stream` chunks now carry `request_id`/`provider`, and
  `RequestRegistry::is_streaming_allowed` drops chunks once the request is
  cancelled or terminal, so a late chunk cannot pollute a newer request's
  preview (`late, foreign and post-cancel chunks are dropped at the frontend`,
  plus the Rust-side gate).
- Provider switching: an event for a non-active provider/request is ignored; a
  response is never attached to whichever provider happens to be selected.
- Conversation identity: web requests carry the conversation ID and the
  provider chat is reused per conversation and reset for a new one
  (`provider_chat_is_reused_for_followups_and_reset_for_a_new_conversation`).
  Local providers have no runtime conversation ID — documented limitation, the
  task ID is the strongest available identity.
- Concurrency: the existing "one agent task at a time" limit is preserved; the
  registry keeps each request's state isolated so one provider's failure cannot
  corrupt another's
  (`liveness_and_task_correlation_isolate_requests`).

### Phase G — timeouts, cancellation, recovery

- Local timeouts are configurable per provider (`providers.ollama/lmstudio
  .timeout_secs`, validated in settings) with a 600 s default, and use one
  absolute deadline from submission (a steadily streaming reply cannot extend
  it) → `timed_out` with category `timeout`.
- `submitting → failed` is used for a runtime that cannot be reached
  (`unavailable`) or returns non-2xx (`send_failed`); a mid-stream provider
  error fails with `provider_error` (`local_http_500_fails_as_send_failed`,
  `local_stream_error_fails_as_provider_error`). The ordering ack-before-terminal
  is deterministic (`biased` select), so a 2xx whose body fails always records
  `submitted` before `failed`.
- Cancel aborts the stream task, emits `cancel_requested` then `cancelled`, and
  the earlier `stopped` error is mapped through `reply_wait_state` so cancel and
  timeout are never conflated (`local_cancel_reports_cancel_requested_then_cancelled`,
  `local_timeout_reports_timed_out`, `a_second_wait_emits_no_second_terminal`).
- No durable cross-restart recovery is claimed: the registry is in-memory only.

### Phase H — frontend

- `ui/src/providerStatus.ts` holds the pure reducer/contract: state labels, the
  terminal-state guard (late transitions after a terminal state cannot repaint
  the UI), streaming-chunk correlation (append for deltas, replace for
  partials), and metadata-only diagnostics.
- `App.tsx` reduces every `provider-request-state` event, keeps the last 20
  states, clears the preview only on terminal states, and surfaces a one-time
  warning for unconfirmed submission and for rejected pushes — never page text.
- `Chat.tsx` renders `ProviderWaitCard` for **web and local** providers with the
  real state ("Request: submitted"), the provider ID, and a rejection note when
  a push was refused. Loading indicators stop on every terminal state.

### Phase I — diagnostics

- `ui_request_log` returns the bounded, metadata-only registry snapshot

  category). No prompts, replies, cookies, tokens or page text are stored.
- The event contract distinguishes created / submitting / submitted /
  submission_unconfirmed / streaming / completed / failed / timed_out /

## Live failure — the reply is on the website but not in the app (2026-10-23)

Reported from a real session: the ChatGPT reply was visible on the provider page,
the wait card said `Request: submitted · chatgpt`, "Capture current reply" answered
"no complete reply is visible on the provider page yet", and the recorded error read
`provider page changed (selectors may be stale): cannot change provider profile while
an agent task is active`.

### Diagnosis (two independent defects)

1. **Reply detection used one layout family.** `extractedLast()` read only the
   adapter's `messages` selector (`[data-message-author-role="assistant"]`), then fell
   back to "the sibling after the last user turn". Live evidence (2025-2026) shows
   chatgpt.com rotating at least three transcript layouts — role attributes, list
   transcripts (`li[data-message-role]`, prompt inside `button[data-user-message-bubble]`),
   and per-turn wrappers whose `<article>` became a `<section>`. On a rolled-out layout
   the selector returns ZERO nodes, so the watch never sees generation start and the
   backstop finds no candidate — while the answer sits on screen. A zero-node result
   was also indistinguishable from "no reply yet" in the UI.
2. **A provider switch was misreported as page drift.** `send_inner` wrapped every
   mount failure in `ProviderError::PageChanged`, so "the provider window is bound to a
   different profile during a running task" was rendered as "selectors may be stale".
   That sent the user hunting for DOM drift while nothing was wrong with the DOM.

### Fixes

- `adapter_runtime.js`: reply detection now tries structural identities across
  layouts — assistant markers (`data-message-author-role`, `data-message-role`,
  `data-turn`, `data-author`, `data-author-role`, `data-testid="assistant-turn"`),
  the adapter selector, then turn wrappers (`article`/`section`/`li`
  `[data-testid^="conversation-turn"]`) whose role is on the wrapper, on a descendant,
  or in the provider's own "… said" label. Wrappers carrying a user marker are never
  accepted, so a prompt cannot be returned as the answer. Nodes are de-duplicated in
  document order and nested duplicates are dropped (a prompt bubble inside its own turn
  is one turn, not two).
- Content extraction prefers `[data-message-content]`, `.markdown`, `.prose`,
  `.whitespace-pre-wrap` inside a node already identified as an assistant turn (plus
  the existing provider-specific containers), so "ChatGPT said:" chrome is not pushed
  as reply text.
- `page_info` now reports `reply_layout` (`adapter` / `role` / `turns` /
  `user-anchor` / `none`) and the real assistant/user turn counts; `capture_reply`
  reports the same. Both are metadata only.
- `ui_capture_reply` now explains a failed capture with that metadata: which layout
  matched, how many turns were found, and whether the provider was still generating —
  including the explicit "the provider page layout was not recognised at all — this is
  a markup change, not a missing reply" case.
- `ProviderError::ProfileLocked` (category `busy`) replaces the misleading
  `page_changed` wording for a provider switch during a running task, with an
  actionable message ("stop the running task before switching providers"), and the UI
  labels the category "provider window busy". `PROFILE_LOCKED` is a shared constant so
  the send path classifies the case instead of string-matching an inline literal.
- `adapter-chatgpt.json` selectors now cover the list/`data-turn` layouts as well.

### A. Reply capture on a real ChatGPT page (the blocking live defect)

A live session reported, verbatim from the wait card:

`no complete reply is visible on the provider page yet (layout: user-anchor, assistant turns: 2, user turns: 2); the assistant turn was found but carried no text`

That diagnostic (added in the previous pass) identified the failure exactly: the page
exposed **no** `data-message-author-role`, **no** `data-message-role`, and **no**

zero assistant turns and the sibling heuristic returned an empty container while the
answer was visible on screen.

Fixes:

- **Attribute-free content fallback** (`adapter_runtime.js`): when no structural
  marker matches, the newest non-empty content block that appears AFTER the user's own
  turn (and is not inside it) is used. Blocks are matched by content role only
  (`[data-message-content]`, `.markdown`, `.prose`, `[class*="markdown" i]`,
  `.whitespace-pre-wrap`). Detection families are now: `adapter` → `role` → `turns`
  → `content` → `user-anchor` → `none`.
- **The sent prompt can never be returned as an answer**: the runtime remembers the
  prompt it just sent and refuses a block that matches it (including head/tail match
  for long, UI-truncated prompts), which matters on pages that render prompts through
  the same markdown pipeline as answers.
- **Empty marker match falls through**: an attribute match whose text is empty no
  longer short-circuits detection (that is precisely what produced "assistant turn was
  found but carried no text").
- **Structural diagnostics**: `capture_reply`/`page_info` now return a bounded
  `dom` report — newest blocks and their ancestor chain (tag names, `class`/`data-*`
  attribute NAMES, child counts and text LENGTHS; never page text). A failed capture
  writes it to the app log (`capture-miss`) and the card now ends with e.g.
  `— newest block: div.markdown.prose (len 0); ancestors: main > div > section`, so
  the next report is evidence instead of another guess. `data-*` VALUES stay in the
  log, not in the chat card.

### B. A regression I introduced, caught by the tests

The first performance fix memoized reply extraction on a 40 ms timer. That is wrong
for a mutation-driven watch: a single mutation batch samples the previous snapshot and
there may be no second callback to correct it, so eight watch tests failed. Replaced
with a memo keyed on a **DOM version** counter that mutation callbacks increment —
within one batch the DOM is unchanged, so repeated scans collapse, and no change is
ever hidden. Nine tests caught this before it shipped.

### K. Content-script scheduling (item 5, second pass)

The four provider content scripts (`chatgpt.js`, `claude.js`, `gemini.js`,
`generic.js`) each ran a FULL `document.querySelectorAll` pass on **every** mutation of
`<html>` (childList + subtree), and their handler calls `message.textContent`, which
serializes the whole subtree. During streaming that is dozens of full-document passes
per second.

Added `browser-extension/content/scan-scheduler.js` and switched all four scripts to it
(each keeps its own selectors and handler):

- one observer per script, coalescing every mutation into at most one pass per interval
  (default 200 ms);
- only CHANGED nodes are processed (added nodes, their matching descendants, and up to
  four ancestors), never the whole document;
- a full pass happens only on a structural change (container swap, removed node,
  first load) or when the tab becomes visible;
- `data-neelima-own` marks the review button/panel, and mutations caused by them are
  ignored — appending our own button no longer re-triggers the provider handler;
- it observes `<main>` when present (upgrading after SPA mount) and falls back to
  `<body>`;
- if the scheduler fails to load, each script falls back to the old scan, so a manifest
  mistake degrades rather than disables the feature.

The manifest loads the scheduler before the provider scripts for chatgpt/claude/gemini
(`generic.js` is not registered in the manifest — unchanged, pre-existing).

### L. Path separation recorded (item 2)

The extension relay and the embedded webview adapter are SEPARATE paths and must not be
treated as interchangeable:

- **Embedded webview adapter** (`adapter_runtime.js` + `webprov.rs`): submits prompts,

## Scope and decision record

Goal: give a task the files it needs without loading the workspace, without network
access, and without weakening any Step 2 guarantee.

1. **Retrieval is lexical and in-memory** (`src-tauri/src/context.rs`). One
   `ignore` walk (`.gitignore`, hidden and generated trees skipped), candidates
   sorted by path for determinism, BM25-style scoring with a file-name boost, and
   contiguous excerpt windows for files that do not fit whole. No index is written
   to disk and none is read back.
2. **The prompt is assembled in Rust, not the UI.** `agent.rs` computes the block
   before the first send and inserts it between skills and prior-conversation
   context, ahead of `TASK:`. An empty selection produces an empty string, so a
   no-context prompt is byte-identical to Step 2 — the unchanged agent e2e prompts
   and the explicit no-match test both demonstrate this.
3. **Budgets are per provider family, not a constant.** `Settings.context` holds
   web (6,000 default), local (2,500) and file cap (12), validated at save time
   and clamped again at use; `Provider::context_kind()` maps the selected provider.
   The rendered block is shrunk excerpt-by-excerpt until it fits, so the byte bound
   holds rather than being "usually true".
4. **Preview and send share one function.** `ui_context_preview` calls the same
   `context::select_for` as `ui_task_start`/`ui_task_continue` and returns metadata
   only (paths, line ranges, sizes, counts). The composer's `ContextPicker` lists
   those files, allows per-file veto, and can disable context for the task. The
   agent's transcript entry is the authoritative record of what was attached; the
   app log records counts and flags only, never file contents.
5. **Honesty over silence.** Truncation, scan limits and skipped binary/oversized/
   unreadable files appear in the prompt block, the transcript note and the UI
   caveat. If nothing matches, the transcript says the prompt was sent without
   files.
6. **Dropped from the plan:** cross-file import/`mod` expansion. It needs
   per-language parsing, and the preparation plan made it conditional. Recorded as
   a limitation, not silently skipped.

message, one `user` role, no system/developer role, one-line wire body with escaped newlines, hostile text
